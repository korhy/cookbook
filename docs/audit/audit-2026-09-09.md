## Addendum — corrections and outcomes (same day, after phases 1–4)

**Finding #36 was wrong and is withdrawn.** The audit claimed `SlugListener::preUpdate` silently
does nothing because Doctrine computes the change set before dispatching `preUpdate`. That rule is
real in general but not for this ORM: `UnitOfWork::executeUpdates()`
(`vendor/doctrine/orm/src/UnitOfWork.php:1133-1137`, ORM 3.5.8) calls
`recomputeSingleEntityChangeSet()` immediately after invoking the listeners, unconditionally
whenever any `preUpdate` listener is registered. A plain setter there *is* picked up.
`SlugListenerTest::testRenamingARecipeRegeneratesTheSlugOnUpdate` proves it against the database.
What survived of #36 is only that the behaviour was untested — it now is.

**New finding, #40 — `recipe.slug` has no unique index.** `#[UniqueEntity('slug')]` is
validation-level only, and `ImportCsvCommand` persists without running the validator, so duplicate
slugs are reachable. `RecipeRepository::findOneBySlug()` uses `getOneOrNullResult()`, which means a
duplicate does not resolve to the first row — it makes `recipe_get` raise
`NonUniqueResultException`. Characterised by
`RecipeRepositoryTest::testDuplicateSlugsMakeFindOneBySlugThrowRatherThanPickOne`. **Not fixed** —
adding a unique index needs a migration against production data and is a decision for the user.

**Correction to the consumer-impact section.** `recipeIngredients` and `instructions` serialize as
nested *hydra collections*, not plain arrays: Radiant iterates `recipe.recipeIngredients.member` and
`recipe.instructions.member` (`radiant/templates/app/cookbook/recipe.html.twig:68,89`). Flattening
either into a bare list would empty both loops without raising. Now asserted by
`RecipeSerializationTest::testNestedCollectionsKeepTheHydraMemberShape`.

**On the `LocaleListener` default (#15).** It cannot be exercised through the API test client:
`Request::create()` hardcodes `HTTP_ACCEPT_LANGUAGE: en-us,en;q=0.5`
(`vendor/symfony/http-foundation/Request.php:334`), so a "header-less" test request is not actually
header-less. Both locales are asserted explicitly instead. The finding itself stands, unfixed.

## Consumer impact — what would break Radiant

Sequence these with the Radiant repository, and mark them `feat!:` / `BREAKING CHANGE`.

**Breaking if changed:**

- **`order[slug]`** — Radiant maps its own `order[title]` onto it
  (`radiant/src/Controller/CookbookController.php:53`). The name is already dishonest: sorting "by
  title" is implemented as ordering by `slug`. Renaming it to `order[title]` would be right, and it
  is a major bump.
- **`thumbnail` as an absolute URL** — built by `src/Serializer/RecipeNormalizer.php:30` and rendered
  directly by `RecipeCard.html.twig` and `recipe.html.twig`. Returning a bare path breaks both.
- **`status` on `recipe:read`** (#2) — dropping it is breaking, even though it is a constant.
- **Fields Radiant reads**: `id`, `title`, `description`, `duration`, `thumbnail`, `category`,
  `recipeIngredients`, `instructions`. It does **not** read `slug`, `createdAt` or `updatedAt` — but
  those are on the published contract regardless.
- **`order[duration]`, `order[createdAt]`, the `title` filter, the `category` IRI filter** — all sent
  by Radiant.

**Not breaking for Radiant:**

- #1 (excluding drafts from `/api/v1/instructions` and `/api/v1/recipe_ingredients`) — Radiant never
  calls those endpoints.
- #7 (capping `category_list`) — Radiant uses REST, not MCP.
- #4 (dropping the unused `denormalizationContext`s) — no write operation is registered.

## Explicit "keep" list

Do not "fix" these — each is deliberate:

- **The API is read-only** (`GetCollection` + `Get` only, pinned globally in
  `config/packages/api_platform.yaml`). A design decision, not an omission. Writes happen in
  EasyAdmin.
- **`>=8.2` in `composer.json` while everything runs 8.4** — CI, the OVH host and the dev container
  are all 8.4. The floor is cosmetic.
- **`config/reference.php` excluded from php-cs-fixer** — the production server rewrites that file,
  and `deploy.yml` runs `git checkout --` on it before pulling. Never reformat or commit it.
- **`.env` committed with non-secret defaults**, `MCP_WRITE_TOKEN` empty — the write tools refusing
  every call by default is the intended fresh-deploy state.
- **`.env.local` on `127.0.0.1:5435` while the container gets `database:5432`** — both correct,
  coexisting on purpose.
- **`Recipe::$status` on the public read contract** (#2) — asserted by a test.
- **The `access_control` ordering** (#14) — correct as written; fragile by nature, not by mistake.
- **`assets/controllers/csrf_protection_controller.js`** — genuinely used, unlike its neighbour.
- **`McpWriteGuard`** — clean. Uniform denial message, fingerprint-only logging, brute-force budget
  charged only on failure, `getRemainingTokens()` rather than `isAccepted()` for the peek. It is the
  best-tested class in the project (12 tests) and needs nothing.
- **`SsrfGuardedFetcher` and `JsonLdRecipeExtractor`** — 15 and 13 tests respectively, covering
  redirect chains, blocked ranges, oversized bodies and address non-disclosure. Leave them alone.
- **The two translation catalogues** — `messages.fr.yaml` and `messages.en.yaml` have identical key
  structure. No drift.
